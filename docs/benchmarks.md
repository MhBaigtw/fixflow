## Index decisions (EXPLAIN evidence)

**Method.** `scripts/index_experiment.py` captures the exact SQL the list endpoint emits for each subject. For each candidate index it runs `CREATE INDEX` + `ANALYZE` inside a transaction, `EXPLAIN (ANALYZE, BUFFERS)` each query 7 times (median execution time), then **rolls the transaction back**. Statistics were refreshed with `VACUUM ANALYZE` first. Times are Postgres execution time only, measured on the 10k dataset above.

| Candidate | Query it targets | Without (ms) | With (ms) | Plan change | Decision |
|---|---|---:|---:|---|---|
| `(created_at DESC, id DESC)` | manager list page (default order) | 17.77 | 0.36 | Seq Scan + top-N sort of all 10,008 rows → `Index Scan using exp_created`, stops after 39 rows | **added** as `req_created_idx` |
| same | manager `?overdue=true` page | 8.08 | 1.20 | Seq Scan → Index Scan (42 rows read) | (same index) |
| same | tenant list page | 0.70 | 0.71 | not used (the unit_id index already serves it) | n/a |
| `(assigned_to_id, created_at DESC, id DESC)` | contractor list page | 7.77 | 0.19 | Bitmap Heap Scan of 3,761 rows + sort → `Index Scan using exp_assigned`, 20 rows | **added** as `req_assignee_created_idx` |
| `(sla_due_at)` | manager `?ordering=sla_due_at` page | 18.25 | 0.32 | Seq Scan + sort → Index Scan, 35 rows | **added** as `req_sla_due_idx` |
| partial `(sla_due_at) WHERE status NOT IN (resolved, closed, cancelled)` | manager `?overdue=true` count | 6.13 | 2.63 | Seq Scan → Bitmap Index Scan | **rejected**: saves ~3.5 ms on one filtered count, the page is already served by `req_created_idx` (1.2 ms), and it adds write cost on every status change |

## Analysis: Baseline vs Optimized

What changed between the two runs (commit `acc01eb`):

1. `select_related("unit")` in `requests_visible_to`, which removes the per-row unit lookup.
2. The three indexes above.
3. Transitions lock with `select_for_update(of=("self",)).select_related("unit__property")`. This is not on the benchmarked GET paths.

- **Queries per list page: 23 → 3** for every role. This is the reliable result: it doesn't depend on hardware, and `tests/test_query_counts.py` pins it, including a test that the count is the same for 5 and 20 rows.
- **List p50: about 3x faster:** manager 67.8 → 21.0 ms, tenant 56.4 → 20.9 ms, contractor 67.5 → 18.2 ms. Both the saved round trips (20 per page) and the indexes contribute. In the database the page query dropped from ~23 ms to ~0.4 ms (manager), so the remaining ~20 ms is mostly Python: JWT verification, DRF serialization of 20 rows, JSON rendering and the test-client overhead. **Further gains would have to come from the app layer, not the database.**
- **Detail p50: about 10–20% faster** (3 → 2 queries). That's small, and within about 2x the noise band.
- **Events and comments: no code change.** Their p50 moved 15–20% between runs. Treat that as noise, not improvement.
- **p95:** the contractor list's 116.6 → 22.8 ms looks dramatic, but the baseline repeat measured 70.7 ms for the same code. The fair before/after p95 is roughly 70–117 → 23–25 ms.
- **Nothing got slower** in these measurements. The indexes do add a small write cost; it wasn't measured here because the benchmark covers reads only.
- **Caveats:** this is one laptop, one local Postgres and an in-process client. Over a network with gunicorn, each saved query also saves a network round trip to the DB, so the query-count reduction should matter *more* in production than it does here. That's an expectation, not a measurement.
