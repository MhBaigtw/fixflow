## What was built

### Part A: architect review fixes
- **A1:** login accepts the email in any case and with surrounding whitespace (`EmailTokenObtainPairSerializer`).
- **A2:** priority ownership.
  - `requested_priority` (the tenant's choice) is separate from the working `priority`.
  - The manager may change `priority` by PATCH or on `triage` while submitted, triaged, assigned or in_progress; after that it's 409 `priority_not_editable`.
  - Every priority change recomputes the SLA.
  - A data migration backfilled the new field (split in two so NOT NULL is set after the backfill commits).
- **A3:** `RequestEvent.event_type` (`status_change` | `edit`) and `changes` (a field-level diff, including `sla_due_at`).
  - Each PATCH that changes something writes exactly one `edit` event; a no-op PATCH writes nothing and doesn't touch `updated_at`.
  - Triage with a priority change records it inside its `status_change` event.
- **A4:** a duplicate unit label that races past the serializer check returns 400 (service plus savepoint), not 500.
- **A5:** the concurrency test docstring now describes what the tests actually assert.

### Part B: baseline (Phase 3)
- `seed_bulk`: deterministic per `--seed`, idempotent, DEBUG-only unless `--force`, and it writes coherent event chains. The real run took 14.1 s for 10,000 requests, 46,118 events and 17,423 comments.
- `scripts/benchmark.py`: in-process, CaptureQueriesContext, 20 warmup + 200 timed requests, p50/p95/max, appending to `docs/benchmarks.md`.
- The baseline was committed (`1422f53`) before any optimization.

### Part C: optimization (Phase 3)
- `select_related("unit")` in the visibility selector cut list queries from 23 to 3.
- `lock_request()` = `select_for_update(of=("self",)).select_related("unit__property")`, so permission checks need no extra queries and only the request row is locked.
- Three indexes, each justified by a rolled-back `EXPLAIN (ANALYZE, BUFFERS)` experiment (`scripts/index_experiment.py`). A partial open-SLA index was tested and rejected.
- Query-count regression tests (`tests/test_query_counts.py`).

### Part D: hardening and stats (Phase 3)
- `ScopedRateThrottle` scopes, set from env:
  - `login` and `token_refresh`: 10/min per IP
  - `writes`: 60/min per user (POST/PATCH only)

  A 429 uses the standard error shape plus `retry_after_seconds` and `Retry-After`.
- `DatabaseCache` holds the shared counters (verified across 2 local processes and 2 live gunicorn workers). Tests use LocMem, cleared per test.
- `GET /api/stats/`: open counts by status, overdue count, and median hours to resolve per category via `percentile_cont(0.5)` in Postgres. Tested with hand-computed medians, including even-count interpolation.

### Parts E and F: deploy (Phase 4)
- **Config:**
  - `render.yaml`: free plan, native Python, `/api/health/` health check, `checksPass` auto-deploy, `SECRET_KEY` generated by Render.
  - `bin/render-build.sh`: migrate, createcachetable, and `seed_demo` if `DEMO_PASSWORD` is set (no pre-deploy command on free).
  - `prod.py`: `sslmode=require`, `CONN_MAX_AGE=60` + `CONN_HEALTH_CHECKS`, and Render's hostname added to `ALLOWED_HOSTS` and `CSRF_TRUSTED_ORIGINS`.
  - `.python-version` pins 3.13 (Render's default is 3.14).
  - CI now boots the Docker image with gunicorn against Postgres and checks the HTTPS redirect behaviour.
- `docs/deploy.md`: free-tier terms with sources, and the setup steps Humayun followed.
- README rewritten: live URL, public demo logins, Mermaid architecture diagram, before/after table, live latency.
- `docs/resume-bullets.md`: 3 bullets, every number linked to its evidence.

## Decisions beyond the prompt (full reasons in docs/decisions.md, D18–D27)

- **D19:** manager priority changes after `in_progress` get a new 409 code, **`priority_not_editable`**, separate from the tenant's `request_not_editable`.
- **D19:** sending `priority` with any action other than triage is 400.
- **Test change (D19):** `test_only_creator_edits` no longer includes the manager-PATCHes-title case, because the spec changed it from 403 to 400. That case now lives in `test_manager_can_patch_priority_only`, asserting 400. This follows the requirement change; it doesn't weaken the test.
- **D22:** open requests in `seed_bulk` are recent (exponential age, mean 8 days), so the overdue share is realistic (measured 17% of all requests).
- **D23:** benchmark conclusions rest on p50 and query counts only, because p95 moves 40%+ between identical runs on this laptop. A repeat run is reported next to each table.
- **D23:** no index for `ordering=priority` (a CASE sort, 8.5 ms); no measured need.
- **D24:** `NUM_PROXIES` defaults to 0 so local `X-Forwarded-For` can't be spoofed.
- **D25:** an out-of-scope `property` on `/api/stats/` returns zeros, not 404 (consistent with the list filters).
- **D26:**
  - Native Python runtime on Render, not Docker; Docker isn't documented for free instances.
  - Migrations run in the build step.
  - Neon **direct** connection, not pooled.
- **D27:** `NUM_PROXIES=3` was measured on the live service after 1 and 2 both failed (see below).
- **Demo password:** because the logins are public, a new throwaway password (`demo-YVD2LQlb020I`) was generated and published. The local `.env` value was never used live or printed.

## Known gaps, risks, surprises

- **Surprise 1: the proxy depth.** Render's official docs don't state the `X-Forwarded-For` hop count. Two reasonable guesses left the login throttle silently ineffective, and local tests couldn't have caught it because they only knew the chain shapes I had assumed. If Render or Cloudflare change their topology, the count changes; the live check is in `docs/deploy.md` section 4. **Not verified:** that two *different* real clients get separate buckets (that needs a second network). Optional check: after being throttled on Wi-Fi, log in from a phone on mobile data; it should not be 429.
- **Free-tier performance:** a ~47 s cold start; warm medians of 0.4–0.8 s, with outliers up to 20 s whose cause wasn't isolated. The laptop benchmark is a controlled measurement of app + DB cost, **not** production latency, and the README says so.
- **Benchmark limits:** one laptop running other software. p95 is unreliable and only p50 and query counts are used for claims. Writes weren't benchmarked, so the indexes' write cost is unmeasured.
- **Public demo:** anyone can change demo data within the role rules (throttled). Redeploys reset passwords and re-create missing seed rows but don't delete visitors' data.
- **Neon storage:** 1 GB per project. The demo is tiny, but the 10k benchmark set was never deployed.
- **Local test runtime today:** the suite took ~14 minutes instead of ~60 s because the machine was heavily loaded by other apps (CPU 56%; browser, other AI apps, Malwarebytes). CI runs it in about 15–25 s. Not a code change.
- **Not done:** an expression index for priority ordering; edits to comments (comments are create-only by design); a `docker compose up` run (CI covers the image).
